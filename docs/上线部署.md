# 上线部署准备

本文对应当前仓库代码，采用「同一 HTTPS 域名：Nginx → 网关 8090 → 后端 8080」方案。仓库未连接任何服务器、云账号或支付账户；下面是可审查的配置样例，不是已经完成的线上部署。

## 服务与数据

| 服务 | 用途 | 必须持久化或备份的内容 |
| --- | --- | --- |
| Nginx | HTTPS、前端静态文件、API/WebSocket 反代 | TLS 证书与配置；前端发布目录建议保留可回退版本 |
| Java 17 后端和网关 | 业务 API、消息连接、请求入口 | 应用配置及必要日志；密钥不放在静态网站目录 |
| MySQL | 用户、商品、订单、资金、纠纷等主数据 | 数据目录、定期备份与恢复演练 |
| Redis | 登录、验证码、缓存、分布式锁 | 按服务配置持久化 AOF/RDB；不要把数据库或缓存暴露公网 |
| RocketMQ NameServer/Broker | 商品审核/搜索同步、订单延迟消息 | Broker 的 store 与配置目录；服务重启后仍需恢复消息 |
| Elasticsearch | 商品搜索 | 数据目录、索引重建流程；主数据以 MySQL 为准 |
| COS 图片存储 | 当前商品、头像、证据图片上传 | 存储桶对象；配置访问域名与生命周期，不能随应用容器销毁 |
| XXL-JOB（按需） | 项目中采用 XXL-JOB 的维护任务 | 调度中心数据库及执行器日志；订单退款/自动确认另有 Spring 定时任务 |

仅发布前端 `dist` 不能启动完整业务。`local/` 是本机运行工具，不是生产部署包，不应上传其中的账号文件或本机数据。

可将服务器数据目录统一放在 `/srv/hue/data/mysql`、`/srv/hue/data/redis`、`/srv/hue/data/rocketmq`、`/srv/hue/data/elasticsearch`，分别映射到实际服务的 `datadir`、`dir`、`storePathRootDir`、`path.data`。执行器默认日志在应用工作目录的 `logs/xxl-job`，可映射到 `/srv/hue/logs/xxl-job`；证书样例目录为 `/etc/nginx/tls/hue/`。容器内目录以选用镜像与服务配置为准，挂载后核验服务账号读写权限。

新库先使用仓库 SQL 初始化，并按版本应用增量迁移；本轮订单新增 `trade_type` 快照也需要对应迁移。对已有线上库先备份并核对结构，不要直接重放包含演示数据或重建表的初始化 SQL。

## 构建与配置

前端使用仓库要求的 Node 版本运行 `npm ci`、`npm run build`，发布 `Nowl-front/dist/` 内容到 `/srv/hue/frontend/`。生产 `VITE_API_BASE_URL=/api`，此方案不需要写死后端公网地址。

后端可用 Java 17/Maven 构建，或在 `Nowl-backend/` 目录分别构建两个镜像：

```sh
docker build -f Dockerfile -t hue-backend:release .
docker build -f Dockerfile.gateway -t hue-gateway:release .
```

镜像仅包含应用，不会自动启动 MySQL、Redis、MQ 或 ES。`deploy/production.env.example` 只含占位配置；复制到服务器受限目录后填写，并通过进程管理器或 `docker --env-file` 注入。Spring Boot 不会自动读取任意 `.env` 文件。

必须核对的配置：

| 配置 | 要求 |
| --- | --- |
| `DB_URL/DB_USERNAME/DB_PASSWORD` | 指向已经初始化并迁移的实际数据库，使用应用账号 |
| `REDIS_HOST/PORT/PASSWORD` | 后端与网关连接同一套 Redis，配置符合实际认证方式 |
| `ROCKETMQ_NAME_SERVER` | NameServer 可达，且 Broker 广播地址也必须能被应用访问 |
| `ES_HOST/ES_USERNAME/ES_PASSWORD` | 当前自定义客户端要求 `主机:端口`，如 `127.0.0.1:9200`，不能填写 `http://`；当前未开启SSL配置，连接只开放在受控内部网络，接入HTTPS ES前需扩展客户端SSL配置 |
| `JWT_SECRET` | 独立生成的 Base64 随机密钥，至少 32 字节；不要沿用开发示例 |
| `UM_BACKEND_URI/UM_BACKEND_WS_URI` | 网关到后端的内部 HTTP/WS 地址；容器内 `127.0.0.1` 只代表本容器 |
| `SERVER_ADDRESS` | 同机进程方案可绑定 `127.0.0.1`；独立容器内需改为 `0.0.0.0` 并限制端口发布/内部网络 |
| `TRUSTED_PROXY_IPS`（网关）、`SECURITY_TRUSTED_PROXY_IPS`（后端） | 只包含各自实际可信反代地址；存在额外 CDN/负载均衡时重新核对来源链 |
| `COS_*` | 有效桶/凭证/区域；`COS_BASE_URL` 必须是带 `https://` 的实际可访问图片地址 |

后端默认 8080、网关默认 8090；不要给二者共用同一个 `SERVER_PORT` 覆盖值。数据库、Redis、MQ、ES、后端及网关只需在可信内部网络互通，公网入口使用 Nginx 80/443。

## 域名、CORS 与 WebSocket

将 `deploy/nginx/hue.conf` 放入 Nginx 的 `http {}` 包含目录，例如 `/etc/nginx/conf.d/hue.conf`。先替换域名、证书路径、前端路径以及网关地址，再执行 `nginx -t`，通过后重载。样例假设 Nginx 是最外层入口；如果前面还有 CDN/负载均衡，应相应配置可信真实来源解析。

样例的 `proxy_pass http://hue_gateway/;` **末尾斜杠需要保留**：

| 浏览器请求 | 网关看到的路径 | 后端看到的路径 |
| --- | --- | --- |
| `/api/goods` | `/goods` | `/goods` |
| `/api/auth/login` | `/auth/login` | `/auth/login` |
| `/api/ws/chat` + Upgrade | `/ws/chat` | `/ws/chat` |

这与当前网关的普通 HTTP 路由和无 `/api` 的 WebSocket 路由相匹配。不要只把 `/api` 原样转到 8090：当前普通 HTTP 路由不会移除这个前缀。聊天和通知会自动跟随当前网站域名使用 `wss://.../api/ws/chat`，样例已传递 Upgrade/Connection。

同步配置以下三组来源，均使用实际完整来源，如 `https://campus.example.edu`，不要附带路径或末尾斜杠：

- 后端 CORS：`SECURITY_CORS_ALLOWED_ORIGIN_PATTERNS`。两个后端 CORS 入口共用同一配置源；不设置时仍保留 localhost/127.0.0.1 开发默认。
- 网关 CORS：`UM_CORS_ALLOWED_ORIGIN_PATTERN_1`、`UM_CORS_ALLOWED_ORIGIN_PATTERN_2`。单域名时两者可填写同一来源。
- 后端 CSRF：`SECURITY_CSRF_ALLOWED_ORIGINS`。它与 CORS 是独立校验，必须同步配置，不能通过关闭鉴权或 CSRF 解决跨域问题。

如未来改为前后端不同站点，Cookie、CSRF Token 和 WebSocket 地址都需额外验证，不能只改 `VITE_API_BASE_URL`。当前样例采用同源部署。

## 仍需完成的业务配置

- **图片：** 当前上传直接使用 COS，没有本地磁盘降级。单设 `UPLOAD_PATH` 不会让商品上传改为本地保存。未配置 COS 时，普通用户不能完成带新图片的商品发布。上传后实际打开返回的图片地址，确认 HTTPS 和读取权限；后台凭证不能进入前端环境变量。
- **短信：** 注册及找回密码依赖短信验证码。只有配置真实 `SMS_SPUG_URL` 后才启用 `SMS_ENABLED=true`。关闭或缺少地址时接口明确报「短信服务尚未配置」，不会再假报已发送。公开注册前必须验证真实接收链路。
- **审核：** 保留自动审核时配置兼容的模型服务及 `OPENAI_*`；服务调用失败会进入人工复核队列，需要管理员处理后商品才会上架。不要将服务失败当成审核通过。
- **资金：** 当前是站内余额扣款/结算，未接入在线充值、第三方支付和提现。不能把页面的余额付款当作已接入真实收款；面向真实交易开放前需补齐资金来源、支付回调、流水及提现结算方案。

本方案不要求新开任何指定平台账号，也不含付费服务购买操作。COS、短信和模型是否继续使用现有提供方，应在准备真实账号与额度时再确定。

## 上线验收

1. 在目标服务器核对环境变量、数据库迁移和持久化目录；重启应用后验证数据仍在。
2. 执行 `nginx -t`；HTTPS 访问首页及直接刷新 `/profile/my-orders`，应能返回前端页面。
3. 请求 `/api/school/list` 等实际公开接口，确认返回 JSON 而非前端 HTML；登录后刷新页面保持会话，写请求通过 CSRF 校验。
4. 登录后确认 `/api/ws/chat` 返回 101 并能实际收发消息。
5. 上传新图片、发布商品、人工/自动审核，再使用专门验收账户验证下单、付款、交付和退款。

反代 URI 替换和升级头规则参考 [Nginx proxy_pass 官方说明](https://nginx.org/en/docs/http/ngx_http_proxy_module.html#proxy_pass) 与 [WebSocket 官方说明](https://nginx.org/en/docs/http/websocket.html)。
